设备启动时，除了拉起进程、初始化硬件，还要重新加载上一次保存的业务配置。这次问题就出在启动配置加载阶段。原设备加载同一份命令行文本配置时，配置恢复能在预期时间内完成；部分设备换成自研 I/O 驱动和性能较低的存储后，配置恢复明显变慢，业务恢复和现场部署也随之受影响。

排查确认，耗时主要不在配置对象下发后的业务处理，而在更前面的文件读取和分词阶段。新的 I/O 路径放大了历史代码中高频单字节读取的成本，但不能因此直接把问题归因于存储设备。本文记录定位和修复过程，也补充说明：当时没有采集块设备等待数据，如果继续怀疑存在 I/O 阻塞，还需要如何验证。


## 配置加载为什么影响设备恢复

设备使用命令行文本格式保存启动配置。加载过程可以概括为：

![load-config](https://raw.githubusercontent.com/ChnjFan/img-bed/master/img/20260902113929741.webp)

这里要区分两种耗时。“读取文件和分词耗时”只统计配置文本转换为配置对象之前的前半段；从设备启动到全部业务配置生效的端到端耗时，还包括业务模块异步接收、处理和应用配置的时间。

典型配置文件约 80MB，包含 100 多万条命令。单条命令平均约 80 字节，行首通常有 4～8 个缩进空格。原设备上，端到端配置加载可以控制在 10 分钟以内。部分设备改用自研 I/O 驱动和性能较低的存储后，其他硬件条件基本不变，但读取和分词从秒级增长到约 10 分钟，端到端耗时接近 20 分钟。配置最终仍能恢复，只是设备重启后的业务可用时间被拉长了。

刚看到这个现象时，很容易先怀疑新存储或新驱动。但设备启动变慢本身说明不了问题出在哪一段：可能是配置文本读取，也可能是命令解析，或者业务模块异步生效。因此，排查先从分阶段统计和 `perf` 采样开始，再逐步收敛到具体调用路径。


## 先把十分钟定位到读取和分词阶段

端到端耗时接近 20 分钟，先要弄清楚的不是“新存储到底慢在哪里”，而是“这将近 20 分钟分别花在了哪里”。

配置加载横跨多个阶段：读取文件、处理行结构、分词和命令解析、生成配置对象，以及将对象异步下发给业务模块后等待其处理完成。只看“全部配置生效”的总时间，无法判断应该优化哪一段。

因此，先在加载流程的阶段边界记录耗时。统计结果表明，新增耗时主要集中在前半段的“读取配置文件和分词”。

| 阶段 | 原设备 | 新 I/O 路径与低性能存储设备 |
| --- | --- | --- |
| 读取配置文件和分词 | 秒级 | 接近10分钟 |
| 启动到全部业务配置生效 | 10分钟以内 | 接近20分钟 |

后半段的业务模块处理仍然需要时间，但它不是这次性能劣化中最早出现、增长也最明显的部分。排查范围可以先从整个启动流程收缩到配置文件进入解析器之前的路径。

端到端变慢，不代表每个阶段都要优化。如果一开始就去看业务模块、配置对象分发或线程调度，很可能会把精力花在原本就存在、但并非这次主要增量的耗时上。

不过，阶段统计只能说明问题集中在读取和分词附近，暂时还不能区分：是文件读取本身变慢，还是行首空白和注释识别增加了开销；是分词器或命令解析器的 CPU 消耗升高，还是读取和解析耦合后，某段逻辑放大了另一段的成本。

接下来需要沿着实际调用栈继续看。我使用 `perf` 对配置加载过程采样，再结合源码检查，最终将热点收敛到 `read` 相关调用路径。


## perf 将热点指向 read 路径

阶段统计把问题收敛到“读取配置文件和分词”后，还要继续判断：时间主要花在文件读取，还是花在分词处理。

生产环境中，我用 `perf` 对配置加载过程采样并生成火焰图。热点集中在 `read` 相关调用路径，而不是后续业务模块处理，也没有落在明显的分词计算路径上。

为了确认这个现象不是偶然的，又构造了一套独立的 C++ 复现实验代码，完整代码在 [GitHub 仓库](https://github.com/ChnjFan/CodeGuide/blob/main/C%2B%2B/source/config_loader_demo.cpp)。实验生成约 80MB、100 万条命令的定长文本配置。每条命令约 80B，行首带 4 个缩进空格，并提供两种加载方式：

- `legacy`：扫描行首缩进时，每个字符都调用一次 `read(fd, &ch, 1)`；识别到第一个非空白字符后，再读取该行剩余内容。
- `buffered`：一次填充指定大小的用户态缓冲区，默认 4KB，再在内存中识别缩进、注释和换行。

两种实现都会统计命令数、分词数和命令摘要。只有这些结果一致，后面的性能对比才有意义。

先编译程序并生成配置文件：

```bash
g++ -std=c++17 -O2 -g -fno-omit-frame-pointer \
    config_loader_demo.cpp -o config_loader_demo

./config_loader_demo \
    --file /tmp/config-loader-demo.conf \
    --generate \
    --mode verify
```

编译时，`-g` 用于保留调试信息，`-fno-omit-frame-pointer` 有助于 `perf` 还原用户态调用栈。`verify` 模式会依次运行两种加载器，并检查它们的解析结果是否一致。

在默认生成配置下，旧实现每行会为 4 个缩进空格产生 4 次单字节读取，还会额外读取第一个非空白字符和该行剩余内容。因此，`read_calls` 约为 600 万次，其中约 400 万次来自行首缩进扫描。4KB 缓冲实现的底层读取次数则降到约两万次。两种实现的验证结果一致后，再分别进行采样。

设备性能较高时，可以用 `--repeat 10` 拉长采样窗口；如果目标设备单次加载已经足够久，保留 `--repeat 1` 即可。

```bash
perf record -F 999 -g -- \
    ./config_loader_demo \
    --file /tmp/config-loader-demo.conf \
    --mode legacy \
    --repeat 10
```

将采样数据转换为火焰图：

```bash
perf script | ./FlameGraph/stackcollapse-perf.pl --all \
    | ./FlameGraph/flamegraph.pl \
      --title 'Legacy config loader CPU flame graph' \
    > legacy.svg
```

![](https://raw.githubusercontent.com/ChnjFan/img-bed/master/img/20260902132248682.webp)

再对4KB缓冲实现执行相同操作：

```bash
perf record -F 999 -g -- \
    ./config_loader_demo \
    --file /tmp/config-loader-demo.conf \
    --mode buffered \
    --repeat 10

perf script | ./FlameGraph/stackcollapse-perf.pl --all \
    | ./FlameGraph/flamegraph.pl \
      --title 'Buffered config loader CPU flame graph' \
    > buffered.svg
```

![](https://raw.githubusercontent.com/ChnjFan/img-bed/master/img/20260902132246613.webp)

两张火焰图指向的是同一条读取路径，差别在于这条路径被走了多少次。

旧实现中，用户态的 `__libc_read` 覆盖了 86.46% 的累计样本权重。沿着调用栈继续向下，可以看到 `__x64_sys_read`、`ksys_read`、`vfs_read`、`ext4_file_read_iter`、`generic_file_read_iter` 和 `filemap_read`。其中，`vfs_read` 占 50.10%，`filemap_read` 占 32.57%。旧实现的大量样本都落在文件读取的系统调用和文件系统路径上。

4KB 缓冲版读取的仍是同一份配置文件，但这条路径的占比明显下降：`__libc_read` 为 10.36%，`__x64_sys_read` 为 8.89%，`vfs_read` 为 8.70%，`filemap_read` 为 8.12%。


| 调用帧 | 单字节读取实现 | 4KB 缓冲实现 |
| --- | ---: | ---: |
| `__libc_read` | 86.46% | 10.36% |
| `__x64_sys_read` | 56.61% | 8.89% |
| `vfs_read` | 50.10% | 8.70% |
| `filemap_read` | 32.57% | 8.12% |

这些百分比只表示各自火焰图中的样本构成，不能把矩形宽度直接当成加速比。不过，两次采样使用的是同一份生成配置、相同的重复次数和相同的采样方式。两张图根节点的累计权重分别为 72,938,942,658 和 6,050,748,959，前者约为后者的12.05倍。

这个结果与程序输出相符：`read_calls` 从数百万次降到两万次量级，两种实现解析出的配置结果一致。性能差异主要来自读取调用的粒度，而不是解析结果不同。

缓冲版中最宽的用户态帧是 `hash_byte`，占 37.98%。它用于计算命令摘要，验证两种实现的输出一致。这是复现实验额外加入的校验逻辑，并不是设备中的生产分词器，不能据此把 `hash_byte` 当成优化后的新业务瓶颈。高频小读取消失后，剩余 CPU 时间会更多落在内存扫描、字符串处理和校验逻辑上。真实设备上的下一步，则是继续分析配置对象的异步下发和业务模块生效过程。

这两张 CPU 火焰图也不能证明每次 `read` 都访问了物理存储。调用链进入 `filemap_read`，只能说明程序经过了 Linux 文件读取和 Page Cache 路径。本实验没有通过冷缓存、直接 I/O 或块请求追踪区分缓存命中、缓存未命中和底层设备等待。

因此，这里的结论应限定为：高频单字节 `read` 已经足以让系统调用和文件读取路径成为热点；新 I/O 驱动和低性能存储进一步放大了这段历史代码的成本。是否还存在真实的块设备 I/O 阻塞，需要结合后文的块层数据继续验证。


## 数百万次单字节读取如何放大成本

配置文件约 80MB，单看文件体积并不算特别大，很难让人把它和十分钟级的耗时联系起来。问题不在于总共读了多少字节，而在于为了读完这些字节，程序进入读取路径多少次。

配置中有 100 多万条命令，每条命令前通常带 4～8 个缩进空格。旧逻辑为了跳过这些空格，会对每个字符执行一次：

```c
read(fd, &ch, 1);
```

只计算行首缩进，读取次数就已经是：

```
100万条命令 × 4～8个缩进字符 ≈ 400万～800万次单字节 read
```

这还没有算上读取第一个非空白字符、读取命令剩余内容、处理注释行，以及后续分词可能产生的其他操作。

复现实验使用 100 万条命令、每条约 80B、行首 4 个缩进空格的配置文件。旧实现的 `read_calls` 约为 600 万次，其中约 400 万次用于跳过缩进；其余调用用于识别第一个非空白字符、读取定长命令剩余内容和确认文件结束。4KB 缓冲实现则把底层读取次数降到约两万次量级。

80MB 数据并没有变少，变化的是读取方式：原来大量小粒度的跨边界操作，被合并成了少量批量读取。总成本可以粗略理解为：

```
总耗时 ≈ 读取调用次数 × 单次读取路径成本
        + 用户态扫描与分词成本
        + 可能发生的底层等待
```

这不是精确的性能公式。单次读取的成本会受内核版本、文件系统、缓存状态、驱动和设备负载影响。不过，当调用次数达到数百万级时，即使单次成本不高，累积起来也可能成为主要耗时。

一次 `read(fd, &ch, 1)` 至少需要跨越用户态和内核态的系统调用边界，并进入文件读取路径。即使数据已经在 Page Cache 中，内核仍要处理系统调用、维护文件偏移、查找缓存页，并将一个字节返回给用户态。遇到缓存未命中或底层设备较慢时，单次调用还会叠加文件系统、驱动和存储路径上的额外成本。

前面的火焰图与这一点一致：旧实现的大量样本落在 `__libc_read`、`__x64_sys_read`、`vfs_read` 和 `filemap_read` 路径上；切换到 4KB 缓冲后，同一条路径的样本占比明显下降。即使暂不讨论物理设备等待，高频进入读取路径本身已经是可以测量的 CPU 成本。

原设备上，这段历史逻辑没有造成明显问题，并不代表它没有成本，只是当时单次读取路径足够便宜，累积影响没有显现。切换到新的 I/O 路径和低性能存储后，单次读取的成本上升，数百万次小读取累积起来，最终让读取和分词阶段从秒级增长到约 10 分钟。

这里需要限定结论。现有证据能够支持：

- 高频单字节 `read` 是配置加载中的明确热点；
- 新的 I/O 环境放大了这段历史代码的成本；
- 消除高频小读取后，端到端加载时间恢复到可接受范围。

现有证据不能支持：

- Page Cache 被驱动关闭或失效；
- 每次单字节 `read` 都访问了物理存储；
- 存储设备或驱动是唯一根因。

因此，修复时不必先猜测底层哪一层“最慢”。应用层已经确认存在数百万次小粒度读取，先消除这部分成本更直接。下一节会说明如何将文件读取、行结构识别和分词解耦，并用 4KB 滚动缓冲区处理跨缓冲区命令。


## 将文件读取与分词解耦

定位到高频小读取后，不能只在原来的行首判断中把 `read(fd, &ch, 1)` 改成更大的长度。问题在于，旧逻辑把文件读取、缩进跳过、注释识别和分词放在同一条控制路径上。读取策略被行级语义牵着走：每遇到一个缩进字符就进入一次系统调用，注释判断也可能改变后续读取方式。

优化后，加载流程拆分为四层：

![load-config-nx](https://raw.githubusercontent.com/ChnjFan/img-bed/master/img/20260902151224676.webp)

文件读取层只负责从文件描述符批量取回字节。打开配置文件时创建一个 4KB 用户态缓冲区，每次底层 `read` 尽可能填满缓冲区；加载结束后再释放。设备同一时刻只加载一个配置文件，因此额外内存开销固定为 4KB。

行扫描层在内存中处理行结构：
- 跳过行首空格和制表符；
- 判断第一个非空白字符是否为注释标记；
- 找到换行符后切出完整命令；
- 忽略空行和注释行；
- 将普通命令行交给分词器。

分词器不再关心文件描述符、读取次数或缓冲区边界。它只接收一条完整命令行，再按原有规则生成配置对象。这样，读取粒度由文件读取层统一控制，不会再被行首缩进和注释判断这类局部逻辑打散。

配置对象也不应在读取过程中直接对外发布。加载流程先构建临时配置，只有文件完整读取且命令解析完成后，才向后续业务模块下发。读取失败时，终止本次加载并丢弃临时配置，以空配置启动，同时向用户上报告警。这样可以避免文件读到一半失败，却已经向业务模块下发部分配置的状态。

命令长度同样需要成为读取层与解析层之间的明确契约。本次实现将单条命令限制为 1024B。命令超过上限后，不能只清空当前缓存再继续解析，因为后面的字节仍属于同一条非法命令。正确做法是持续丢弃，直到遇到下一个换行符；随后记录错误，并从下一行继续处理。

4KB 缓冲不意味着每条命令都会完整落在一个缓冲区内。一条命令可能从缓冲区末尾开始，要等下一次读取后才结束；文件末尾也可能没有换行符。下一节会专门处理这些边界，说明滚动缓冲区如何避免跨缓冲区命令被截断、重复或误解析。


## 4KB 滚动缓冲区如何处理跨缓冲区命令

批量读取本身不复杂，容易出错的是命令行边界。4KB 只是一次从文件描述符取回数据的容量，不是命令最大长度，也不是解析器每次必须消费的单位。

一个缓冲区里可能有多条完整命令，也可能只包含某条命令的前半段：

```
[完整命令 A\n][完整命令 B\n][命令 C 的前半段........]
                                ↑
                         尚未结束，不能交给分词器
```

读取层需要维护两个位置：

- begin：当前未处理数据的起点；
- end：缓冲区中实际有效数据的终点。

`end` 不能直接等于4KB。文件尾、短读等情况都会让一次 `read` 返回的字节数小于请求长度，因此只能扫描 `[begin, end)` 这段实际有效的数据。

处理过程如下：
1. 在 `[begin, end)` 中寻找换行符。
2. 找到换行符后，取出从 `begin` 到换行符之前的完整内容。
3. 行扫描层跳过前导空白，识别空行和注释行；普通命令行交给分词器。
4. 将 `begin` 移到换行符之后，继续扫描余下数据。
5. 如果扫描到 `end` 仍然没有换行符，说明当前命令跨越了缓冲区边界。

跨缓冲区时，不能丢弃尾部内容，也不能把它当成一条已经完成的命令。需要把未结束部分前移到缓冲区开头，再从剩余空间继续读取：

```
读取前：

[已处理数据][未结束命令 C........]

前移后：

[未结束命令 C........][空闲空间................]

再次读取后：

[未结束命令 C........][命令 C 剩余部分\n][后续数据...]
```

只有读到换行符后，命令 C 才会作为完整命令交给分词器。

实验中还会测试 128B、512B 和 1KB 等小缓冲区，它们可能小于一条合法命令。此时不能要求未结束命令始终放在当前缓冲区中，需要将已经确认属于同一行的片段暂存起来，直到找到换行符后再拼成完整命令。最终选择的 4KB 缓冲区大于 1024B 的命令上限，大多数跨缓冲区命令只需在缓冲区内前移即可；但实现仍应能正确处理小缓冲区测试场景。

超长命令是另一类必须单独处理的边界。单条命令超过 1024B 时，不能把前 1024B 当成一条命令，再把余下内容误当成下一条命令。读取层应进入“丢弃当前行”状态，持续跳过数据，直到遇到换行符；随后记录非法命令错误，再恢复正常扫描。

文件末尾也不能依赖换行符。最后一次 `read` 返回 0 时，如果缓冲区还有非空内容，这些内容仍是一条文件尾命令，应按普通命令处理；没有残留内容时，解析才真正结束。

读取错误需要和正常 EOF 区分：
- `read` 被 `EINTR` 打断时，重试本次读取；
- `read` 返回 0 时，按实际残留字节处理文件尾；
- 其他错误终止配置加载，丢弃临时配置，以空配置启动并上报告警。

经过这些处理后，缓冲区大小只影响读取粒度，不影响配置语义。无论命令完整落在一个缓冲区内，还是跨越多次读取，分词器看到的都应是同一条完整命令。下一节会说明为什么最终选择 4KB，而不是更小或更大的缓冲区。


## 缓冲区大小为什么选择 4KB

批量读取不等于缓冲区越大越好。缓冲区太小，底层 `read` 调用次数仍然很多；继续扩大缓冲区后，读取次数还会下降，但总加载时间未必继续明显缩短，因为瓶颈可能已经转移到内存扫描、分词或后续业务处理。

因此，在目标设备上分别测试了 128B、512B、1KB、4KB、8KB 和 16KB 的单文件读取缓冲区。测试关注的是配置加载耗时，而不是只比较理论上的系统调用次数。

原始测试数据没有保留可公开的版本，所以这里不绘制精确耗时曲线，也不会把4KB写成适用于所有设备的最优值。能够确认的是：

- 缓冲区从 128B、512B 扩大到 1KB 和 4KB 时，高频小读取带来的开销明显下降；
- 缓冲区达到 4KB 后，加载耗时已经接近收益拐点；
- 继续扩大到 8KB 和 16KB，仍可能减少部分读取次数，但对加载时间的边际收益有限；
- 配置文件只有一个，4KB 的额外内存固定且很小，能够满足设备约束。

最终选择 4KB，是因为在这组目标设备、配置规模和解析逻辑下，它在加载耗时与额外内存之间取得了合适的平衡，而不是因为 4KB 天然优于其他大小。

缓冲区大小测试还必须验证解析结果。不能只确认文件“读完了”，还要检查不同大小下的命令数、注释行处理、跨缓冲区命令、文件尾没有换行符以及超长命令的行为是否一致。否则，较短的耗时可能只是因为部分配置被截断、跳过或误解析。

硬件、文件系统、驱动、配置规模或单条命令上限发生变化后，4KB 都应重新作为一个待测候选值，而不应被固化为默认答案。下一节回到实际设备结果，说明消除高频小读取后，端到端配置生效时间发生了什么变化，以及剩余瓶颈转移到了哪里。


## 优化后配置恢复时间回到可接受范围

这次优化消除了读取和分词阶段中数百万次单字节 `read`。配置文件仍是同一份约 80MB 的文本，命令数量和最终生成的配置对象没有变化；变化的是文件进入解析器之前的读取粒度。

优化后，设备从启动到全部业务配置生效的端到端时间恢复到 10 分钟以内，回到原设备的可接受水平。相比性能劣化后近 20 分钟的恢复时间，设备重启后的业务可用时间重新满足了部署和现场操作的要求。

这个结果需要分两层看。

第一层是读取和分词阶段。4KB 滚动缓冲区消除了行首缩进、注释判断等逻辑触发的高频小读取，前半段不再是启动流程中的主要耗时来源。复现实验中的 `read_calls`、解析结果校验和火焰图共同表明，性能改善并不是通过跳过命令或简化分词得到的，而是通过减少底层读取调用实现的。

第二层是端到端业务恢复。配置对象生成后，仍要异步下发到各业务模块，再由模块完成自身的配置处理和生效。因此，读取和分词恢复到秒级，并不意味着设备从启动到全部业务配置生效也会变成秒级。优化后，剩余的主要耗时集中在业务模块处理配置对象和使配置生效的过程。

```
优化前：

高频小读取
    ↓
读取和分词成为主要瓶颈
    ↓
后续业务处理时间被前半段耗时掩盖

优化后：

批量读取与内存扫描
    ↓
读取和分词不再是主要瓶颈
    ↓
异步业务模块处理成为后续优化方向
```

这次修复解决的是已经证实的应用层读取粒度问题，并不能给新 I/O 路径下所有潜在的性能问题下结论。当时没有单独采集块设备等待、请求延迟或缓存命中数据，因此无法据此排除其他 I/O 问题。下一节会单独讨论：如果怀疑配置加载过程存在真实的 I/O 阻塞，应当怎样建立从进程到块设备的诊断证据链。


## 如果怀疑存在 I/O 阻塞，如何建立证据链

前面的 CPU 火焰图说明，高频单字节 `read` 会让系统调用和文件读取路径成为热点，但它不能说明线程正在等待块设备。CPU 火焰图采集的是线程运行时的调用栈；线程因 I/O 等待而睡眠时，通常不会在图中留下同等比例的样本。

因此，不能只看 `read`、`vfs_read` 或 `filemap_read` 是否出现在火焰图中。要判断是否存在真实的 I/O 阻塞，需要把进程、文件系统和块设备层的数据放到同一时间段内对照。

当时没有采集这组数据，下面给出的是后续排查路径，不是本次故障已经完成的操作记录。

先确认配置文件所在的挂载点和底层设备：

```bash
findmnt -T /tmp/config-loader-demo.conf -o SOURCE,TARGET,FSTYPE
```

如果文件位于逻辑卷、device mapper、RAID 或网络文件系统上，`SOURCE` 未必是最终承载 I/O 的物理设备。后续查看设备指标时，还需要沿着映射关系继续确认。

### 区分高频系统调用和实际存储读取

在配置加载开始和结束时读取进程的 `/proc/<pid>/io`：

```bash
cat /proc/<pid>/io
```

其中三个字段最有价值：

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `syscr` | 读取类系统调用次数 | 判断是否存在高频 `read` 或 `pread` |
| `rchar` | 传递给读取类调用的字节数 | 表示应用请求读取了多少数据 |
| `read_bytes` | 从存储层实际取回的字节数 | 判断是否发生了块设备层读取 |

`rchar` 不受 Page Cache 是否命中的影响；对于块设备文件系统，`read_bytes` 用于统计实际从存储层获取的数据。

如果 `syscr` 增长数百万次、`rchar` 接近文件大小，而 `read_bytes` 很小，说明应用确实在频繁读取，但这些读取大多可能由缓存满足。反过来，如果 `read_bytes` 也明显增长，才有理由继续观察设备层等待。内核对这些字段的定义参考 [Linux /proc/<pid>/io 文档](https://docs.kernel.org/filesystems/proc.html#proc-pid-io-display-the-io-accounting-fields)。

这不是绝对判断。`/proc/<pid>/io` 的统计会受文件系统类型影响，尤其不能直接把块设备文件系统上的解释套用到 NFS、CIFS 等网络文件系统上。


### 观察系统是否存在 I/O 压力

运行配置加载时，同时采集系统级 I/O 压力：

```bash
cat /proc/pressure/io
```

其中：

| 字段 | 含义 |
| --- | --- |
| `some` | 至少有一个任务因 I/O 资源受阻的时间比例 |
| `full` | 所有非空闲任务都因 I/O 受阻的时间比例 |
| `total` | 累计阻塞时间，可用于计算配置加载时间窗口内的增量 |

PSI 只能说明系统在这段时间是否存在 I/O 压力，不能单独证明压力来自配置加载进程。它更适合作为时间相关性证据：如果配置加载变慢期间 `total` 快速增长，加载结束后又恢复正常，才值得继续沿 I/O 路径追踪。


### 观察目标设备的队列与请求等待

确认目标设备后，按固定时间间隔采集扩展指标：

```bash
iostat -x -y 1 /dev/<device>
```

重点关注：

- `r_await`：读请求从进入队列到完成服务的平均时间；
- `aqu-sz`：平均队列长度；
- `r/s`、`rkB/s` 或 `rMB/s`：读取请求数和吞吐量；
- `%util`：设备忙碌时间占比。

`r_await` 同时包含排队和设备服务时间，`aqu-sz` 反映队列长度。对于串行处理请求的设备，`%util` 接近 100% 可能表示设备饱和；现代 SSD、RAID 等并行设备则不能只凭 `%util` 判断性能上限。

更有价值的信号组合是：配置加载期间 `read_bytes` 增长，`r_await` 和 `aqu-sz` 同时出现异常，并且变化只出现在对应设备上。单独看到较高的 `await`，或者看到设备有读流量，都不足以完成归因。


### 必要时追踪块请求的发出与完成

如果进程和设备指标都指向 I/O 路径，可以进一步确认块请求具体在哪个阶段变慢。先检查当前内核是否提供相关 `tracepoint`：

```bash
perf list | rg 'block:.*rq_(issue|complete)'
```

可用时，在配置加载窗口内采集：

```bash
sudo perf record -a \
    -e block:block_rq_issue \
    -e block:block_rq_complete \
    -- sleep 60
```

`block_rq_issue` 表示请求已发给设备驱动，`block_rq_complete` 表示驱动报告请求完成。通过同一请求的发出和完成时间，可以分析设备服务阶段的延迟；如果请求在发给驱动之前已经积压，还需要结合请求插入队列等事件判断排队时间。

块请求事件通常只能确认设备和时间窗口，未必能直接还原“某个进程的一次 `read` 对应某个块请求”。Page Cache 预读、请求合并、其他进程并发 I/O，以及 device mapper 都会改变这种一一对应关系。因此，块层追踪需要和 `/proc/<pid>/io`、设备指标以及配置加载阶段的时间戳一起解读。

## 两组模拟数据如何区分小读取与 I/O 阻塞

同样是“配置读取慢”，高频小读取和块设备 I/O 阻塞的表现并不一样。下面两组数据只用于说明判断方法，不是本次故障的实际采集结果。

### 场景一：高频小读取带来的调用成本

假设运行复现实验中的旧实现。配置文件刚生成不久，数据大多可以从缓存中取得，但行首缩进扫描仍会执行数百万次单字节 `read`。

| 指标 | 模拟观察 |
| --- | --- |
| `syscr` 增量 | 约 600 万 |
| `rchar` 增量 | 约 80MB |
| `read_bytes` 增量 | 接近 0 |
| CPU 火焰图 | `__libc_read`、`vfs_read`、`filemap_read` 占比较高 |
| `iostat` | 目标设备的读请求、`r_await` 和 `aqu-sz` 没有同步异常 |
| `/proc/pressure/io` | `total` 增长不明显 |

这里可以确认的是：应用发起了大量读取调用。设备层没有出现对应的异常信号，因此没有理由把这段耗时直接归因于物理存储。先减少调用次数更合适，把按字符读取改为批量读取即可。

复现实验的 `--read-delay-us` 参数可以把每次读取的固定成本放大：

```bash
./config_loader_demo \
    --file /tmp/config-loader-demo.conf \
    --mode legacy \
    --read-delay-us 1
```

该参数会在每次成功读取后增加固定等待，用来观察“固定成本乘以数百万次调用”对墙钟时间的影响。它不会产生真实块请求，也不会模拟驱动队列、设备延迟或 I/O 等待状态，因此不能拿这组结果证明块设备阻塞。

### 场景二：读取次数不高，但块设备路径变慢

再假设程序已经改成 4KB 批量读取，系统调用次数只有两万次左右，但配置加载仍然很慢。这时可能看到下面这些信号：

| 指标 | 模拟观察 |
| --- | --- |
| `syscr` 增量 | 约2万 |
| `rchar` 增量 | 约80MB |
| `read_bytes` 增量 | 接近80MB |
| CPU 火焰图 | `read` 路径不再主导 CPU 样本 |
| `iostat` | `r_await` 升高，`aqu-sz` 持续增加 |
| `/proc/pressure/io` | `some` 和 `total` 在加载窗口内明显增长 |
| 块请求追踪 | `block_rq_issue` 到 `block_rq_complete` 的时间明显拉长 |

这时的证据链是连得上的：

```
应用发起读取
    ↓
数据需要从存储层获取
    ↓
设备队列和服务时间上升
    ↓
同一时间窗口内出现 I/O 压力
    ↓
块请求完成延迟变长
```

这类数据可以说明配置加载受到了块设备 I/O 路径的影响。但结论到这里就该停下：还不能据此断言是文件系统、自研驱动、存储介质还是请求队列深度的问题。每一层都需要继续采集对应的数据。

两类问题的差别不在于有没有 `read`，而在于 `read` 之后是否出现了相互印证的等待信号：

```
高频小读取：
syscr 很高
    + 设备层平稳
    = 先优化应用层的读取粒度

真实 I/O 阻塞：
read_bytes 增长
    + 设备队列和等待时间升高
    + PSI 或块请求完成延迟同期异常
    = 继续沿块设备路径排查
```

本次故障已经确认的是第一部分：配置加载中存在高频单字节读取，改成批量读取后，配置恢复时间回到了可接受范围。由于当时没有采集第二类所需的块层数据，不能把这次故障写成已经证实的存储阻塞问题。


## 写到最后

这次性能劣化出现在设备更换自研 I/O 驱动和低性能存储之后，但可以直接修复的问题在应用层。配置加载代码要处理百万级命令，每次检查行首缩进和注释时都会执行单字节 `read`，累计形成数百万次系统调用。

复现实验支持这个判断。旧实现的大量 CPU 样本集中在 `__libc_read`、`vfs_read` 和 `filemap_read` 路径上。改成 4KB 批量读取后，读取路径的样本占比明显下降，两种实现解析出的配置结果也保持一致。

修复后，设备从启动到全部业务配置生效的耗时由 20 分钟以上恢复到 10 分钟以内。读取和分词不再是主要瓶颈，后续可以把重点放到配置对象异步下发后，各业务模块的处理和生效过程。

这次排查也留下了一个边界：`read` 路径是热点，说明高频系统调用和文件读取路径消耗了大量 CPU 时间；但它不能证明每次读取都访问了物理存储，也不能证明 Page Cache 被关闭，或驱动本身存在阻塞。现有证据只能支持“新的 I/O 环境放大了历史代码中高频小读取的成本”这一结论。

以后再遇到类似问题，除了保留阶段耗时和 `perf` 采样，还应同时采集 `/proc/<pid>/io`、PSI、设备队列指标和块请求追踪数据。这样才能区分应用层读取粒度过细和块设备路径确实发生等待，避免把热点、症状和根因混在一起。
