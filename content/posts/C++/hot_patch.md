## 补丁加载之后，进程里发生了什么

做 C++ 开发时，遇到线上故障，有时需要用热补丁修复。我接触到的流程是：提交修改后的函数代码，内部工具将它制作成补丁包，再通过统一的管理命令加载，让修复生效。

工具封装了具体实现。使用时，我知道要提交什么代码、执行什么命令，却看不到加载补丁时进程内部的变化。一个已经运行起来的进程，究竟怎样开始执行新函数？这是我想弄清楚的问题。

平时修改代码，我们会重新编译，再启动新程序。新进程加载新的可执行文件，自然也就执行了修改后的逻辑。热补丁生效时，进程却没有重启：原来的代码还在内存里，线程可能正在处理请求，之前创建的对象也都还在。修复后的函数需要在这样的环境中接替旧函数。

这意味着，一次补丁生效至少需要处理下面几个问题：

- 修改后的源码需要编译成机器代码，加载到目标进程中。新代码依赖的函数和数据也必须能在进程中找到。
- 新函数加载进来之后，原来的调用不会自动转向它。补丁机制还需要改变调用的执行路径，让它进入新函数。
- 切换时，可能有线程已经进入旧函数，新函数也可能继续访问原来创建的对象。这些尚未结束的调用和已有状态该怎么处理，不能只靠改变调用方向来回答。

本文讨论 Linux x86-64 环境下的函数级热补丁，重点解释将原函数入口改为跳转到新函数的实现方式，以及其中的加载、切换和兼容性问题。文中的说明依据公开资料和教学示例，不代表内部工具一定采用了相同的实现。

要理解入口处的跳转如何完成替换，需要先看清原来的调用路径：源码里的一次函数调用，编译后对应哪些指令，执行时又怎样进入函数、返回调用处。热补丁改变执行路径的位置，就在这个过程中。


## 没有补丁的一次函数调用如何执行

这段代码中的 `run_once()` 调用 `calculate(10)`，再将返回值乘以 2，按代码逻辑应得到 22：

```cpp
extern "C" __attribute__((noinline))
int calculate(int x) {
    return x + 1;
}

extern "C"
int run_once() {
    return calculate(10) * 2;
}
```

示例中有两处设置是为了方便观察。`extern "C"` 让汇编中的函数符号更容易辨认；`noinline` 阻止编译器将 `calculate()` 内联到调用者中，方便我们观察函数调用。这些是本节示例的设置，并不意味着所有 C++ 热补丁都需要这样的函数声明。

将代码编译为面向 Linux x86-64 的汇编，摘出这两个函数后结果如下：

```asm
0000000000001129 <calculate>:
    1129: f3 0f 1e fa       endbr64
    112d: 55                push   %rbp
    112e: 48 89 e5          mov    %rsp,%rbp
    1131: 89 7d fc          mov    %edi,-0x4(%rbp)
    1134: 8b 45 fc          mov    -0x4(%rbp),%eax
    1137: 83 c0 01          add    $0x1,%eax
    113a: 5d                pop    %rbp
    113b: c3                ret

000000000000113c <run_once>:
    113c: f3 0f 1e fa       endbr64
    1140: 55                push   %rbp
    1141: 48 89 e5          mov    %rsp,%rbp
    1144: bf 0a 00 00 00    mov    $0xa,%edi
    1149: e8 db ff ff ff    call   1129 <calculate>
    114e: 01 c0             add    %eax,%eax
    1150: 5d                pop    %rbp
    1151: c3                ret
```

每行从左到右依次是指令地址、机器指令的字节和对应的汇编指令。这里使用 AT&T 语法，寄存器以 % 开头，立即数以 $ 开头，常见双操作数指令按“源、目的”的顺序书写。例如，mov $0xa,%edi 将十六进制的 0xa，也就是十进制的 10，写入 EDI。参考：[GNU 汇编器语法说明](https://sourceware.org/binutils/docs/as/i386_002dVariations.html)。

`run_once` 中的这三条指令分别负责传参、调用函数和使用返回值：

```asm
1144: bf 0a 00 00 00    mov    $0xa,%edi
1149: e8 db ff ff ff    call   1129 <calculate>
114e: 01 c0             add    %eax,%eax
```

Linux x86-64 通常采用 System V AMD64 调用约定。对于本例的 `int calculate(int)`，参数通过 `EDI` 传入，返回值通过 `EAX` 传回。这两个寄存器分别是 `RDI` 和 `RAX` 的低 32 位。因此，调用者先把 10 放入 `EDI`，调用结束后，再用 `add eax, eax` 将返回值乘以 2。参考：[System V AMD64 ABI 的寄存器使用约定](https://gitlab.com/x86-psABIs/x86-64-ABI/blob/master/x86-64-ABI/low-level-sys-info.tex)。

调用双方必须遵守同一套约定，才能在正确的位置传递参数、读取结果。替换函数后，新函数也需要遵守这份约定。

`call calculate` 中的 `calculate` 是汇编符号。经过汇编、链接等处理，处理器执行这条直接调用指令时，会根据指令中编码的目标信息（例如相对位移）确定调用地址，不会按 C++ 函数名查找源码。

符号如何解析成地址，暂时留到后面。对于本例这样的**普通近调用**，`call` 会完成两个动作：

1. 将紧接着 call 的下一条指令地址压入栈中，作为返回地址。
2. 将执行位置转移到被调用函数的入口。

{{< notice note >}}
**x86 的 `CALL` 可以分为近调用和远调用**。本文示例使用近调用：目标与当前代码位于同一代码段，只更新 `RIP`，不改变 `CS`。远调用还会装载新的代码段选择子。现代 Linux x86-64 用户态程序中的普通函数调用通常使用近调用，本文不讨论远调用。
{{< /notice >}}

`calculate` 用下面两条指令保存调用者的 `RBP`，并以当前栈位置建立自己的栈帧：

```asm
push   %rbp
mov    %rsp,%rbp
```

随后，函数将 `EDI` 中的参数暂存到栈内存，再读入 `EAX`，加上 1：

```asm
mov    %edi,-0x4(%rbp)
mov    -0x4(%rbp),%eax
add    $0x1,%eax
```

这组栈内存读写是本次编译生成的，并非每个函数都需要。经过优化，代码可能直接在寄存器中完成计算。本例也没有用 `sub` 指令额外分配这四个字节，而是使用了栈指针下方的一块临时区域，即 System V AMD64 ABI 允许使用的 red zone。参考：[ABI 对 red zone 的规定](https://raw.githubusercontent.com/wiki/hjl-tools/x86-psabi/x86-64-psABI-1.0.pdf)。

计算完成后，`pop %rbp` 恢复调用者的 `RBP`，栈顶也随之重新指向此前保存的返回地址。`ret` 取出这个地址，程序回到 `run_once` 继续执行。


![run_once_progress](https://raw.githubusercontent.com/ChnjFan/img-bed/master/img/20260901111439075.png)

本例中，调用点、函数入口和返回地址对应的位置分别如下：

| 位置 | 本例中的地址 | 作用 |
|---|---|---|
| 调用点 | `0x1149` | 发起对 `calculate` 的调用 |
| 函数入口 | `0x1129` | 开始执行 `calculate` |
| 返回地址对应的位置 | `0x114e` | 函数返回后，从这里继续执行 |

这些地址只对应当前的反汇编，不能当作程序每次运行时的固定地址。如果程序采用 PIE，计算运行时地址还需要加上装载偏移。不过，上面的相对位移计算仍然成立，因为调用点和目标位于同一个装载模块中。参考：[Linux 装载地址说明](https://man7.org/linux/man-pages/man3/dl_iterate_phdr.3.html)。

热补丁可以在调用点改变目标，让它调用新函数；也可以保留调用点，在旧函数入口将执行流程转向新实现。后文重点讨论第二种方式。

要让这个跳转生效，修复后的函数必须先成为进程中可以执行的代码。它是怎样加载进这个正在运行的进程的？


## 新函数如何进入正在运行的进程

上一节中，`run_once()` 通过一条 `call` 指令进入 `calculate()`。假设新版本已经写好，怎样才能让正在运行的进程执行它？

C++ 源码需要先编译成机器代码，再加载到进程的地址空间。如果新函数引用了其他函数或全局变量，还需要找到这些引用对应的地址。**Linux 的动态加载机制**可以完成这些工作。

本节用共享库 `.so` 承载新函数，演示加载过程。这是教学示例，不代表前面提到的内部补丁包一定采用相同格式。

将新函数保存为 `patch.cpp`：

```cpp
extern "C" int calculate_v2(int x) {
    return x + 2;
}
```

这里把计算改成 `x + 2`，只是为了观察新旧实现的区别，不对应真实故障。新函数保留了原来的参数和返回值类型，名称改为 `calculate_v2`，方便区分两个版本。

用下面的命令将它编译成共享库：

```bash
g++ -std=c++17 -O0 -fPIC -shared patch.cpp -o patch.so
```

`-shared` 指定生成共享库，`-fPIC` 指定生成位置无关代码，使代码能适应不同的装载地址。不过，位置无关代码在装载时仍可能需要处理地址。参考：[GCC 共享库选项](https://gcc.gnu.org/onlinedocs/gcc/Link-Options.html#index-shared)、[位置无关代码选项](https://gcc.gnu.org/onlinedocs/gcc/Code-Gen-Options.html#index-fPIC)。

此时，`patch.so` 还只是磁盘上的文件，加载操作需要在目标进程中执行。**独立工具在自己的进程里调用 `dlopen()`，只会把共享库加载到自己的进程中，不会加载到另一个业务进程里**。本节在示例程序中预留加载入口，通过回车触发。实际的管理命令怎样让目标进程执行这段加载逻辑，则由补丁框架另外解决。

目标进程通过 `dlopen()` 加载共享库，再用 `dlsym()` 查找新函数：

```cpp
void* handle = dlopen("./patch.so", RTLD_NOW | RTLD_LOCAL);
void* symbol = dlsym(handle, "calculate_v2");
```

两个接口返回的内容不同：

- `dlopen()` 返回代表已加载共享对象的句柄，并不是新函数的地址。
- `dlsym()` 根据句柄和符号名查找符号，返回对应的运行时地址。本例查找的是 `calculate_v2`。

参考：[Linux dlopen 手册](https://man7.org/linux/man-pages/man3/dlopen.3.html)、[dlsym 手册](https://man7.org/linux/man-pages/man3/dlsym.3.html)。

加载时，动态加载器会把 ELF 中可加载的代码和数据映射到进程地址空间，并完成必要的重定位。重定位可以先理解为根据实际装载位置和符号解析结果，将地址信息填入需要修正的位置。

本例使用 `RTLD_NOW`，要求共享库中需要解析的外部符号在 `dlopen()` 返回前完成解析，无法解析时加载报错。`RTLD_LOCAL` 控制该共享库的符号是否可供随后加载的共享对象解析使用，不提供安全隔离。如果共享库带有初始化函数，加载时还会执行这些函数，因此加载操作也可能产生副作用。参考：[加载选项与初始化行为](https://man7.org/linux/man-pages/man3/dlopen.3.html)。

把加载和符号查找放进完整的宿主程序 `host.cpp`，代码如下：

```cpp
#include <cstdio>
#include <dlfcn.h>

extern "C" __attribute__((noinline))
int calculate(int x) {
    return x + 1;
}

extern "C" int run_once() {
    return calculate(10) * 2;
}

int main() {
    std::printf("before: run_once() = %d\n", run_once());

    std::puts("Press Enter to load ./patch.so");
    if (std::getchar() == EOF) return 1;

    void* handle = dlopen("./patch.so", RTLD_NOW | RTLD_LOCAL);
    if (!handle) {
        std::fprintf(stderr, "dlopen: %s\n", dlerror());
        return 1;
    }

    dlerror();  // 清除之前的动态加载错误
    void* symbol = dlsym(handle, "calculate_v2");
    const char* error = dlerror();

    if (error) {
        std::fprintf(stderr, "dlsym: %s\n", error);
        return 1;
    }
    if (!symbol) {
        std::fprintf(stderr, "calculate_v2 has a null address\n");
        return 1;
    }

    using Calculate = int (*)(int);
    auto calculate_v2 = reinterpret_cast<Calculate>(symbol);

    std::printf("new: calculate_v2(10) = %d\n", calculate_v2(10));
    std::printf("after: run_once() = %d\n", run_once());

    // 本示例让共享库一直保留到进程退出。
    return 0;
}
```

`dlsym()` 返回空指针，不一定表示符号查找失败。因此，调用前需要清除旧错误，调用后再用 `dlerror()` 检查本次查找是否出错。本例还会单独检查返回的地址，拒绝通过空地址调用函数。参考：[dlsym 错误处理规则](https://man7.org/linux/man-pages/man3/dlsym.3.html)。

取得地址后，程序将它转换为 `int (*)(int)` 并调用。这项转换依赖 Linux/POSIX 动态加载接口的支持，函数指针类型也必须与实际函数匹配。`dlsym()` 只查找符号，不会检查 C++ 函数的参数类型和返回值类型。

编译宿主程序，然后在包含 patch.so 的目录中启动：

```bash
g++ -std=c++17 -O0 -Wall -Wextra host.cpp -ldl -o host
./host
```

按回车触发加载后输出如下：

```
before: run_once() = 22
Press Enter to load ./patch.so

new: calculate_v2(10) = 12
after: run_once() = 22
```

最后两行输出分别是 `12` 和 `22`：通过新函数指针调用时，执行的是新实现；再次调用原来的 `run_once()`，结果仍然没有变化。此时，进程中有两条不同的执行路径：

```
[run_once()]
    |
    v
[原 calculate(10)] --> [返回 11，再乘以 2]


[通过 dlsym 得到的函数指针]
    |
    v
[新 calculate_v2(10)] --> [返回 12]
```

新代码已经加载到进程中，也能执行。但 `run_once()` 的调用指令和原函数入口都没有改变，因此它仍然执行旧逻辑。即使把共享库中的新函数也命名为 `calculate`，仅仅加载它，也不会自动改写上一节的那条直接调用指令。

示例中的新函数只使用传入的参数，没有业务依赖。实际修复的函数可能还需要调用宿主中的其他函数，或访问已有的全局状态。这些引用能否被动态加载器解析，需要逐一确认。例如，主程序中的符号需要进入动态符号表，才能用于解析共享库中的引用，`-rdynamic` 是一种导出方式。不过，导出了符号，并不代表新旧代码一定兼容，也不能保证补丁访问的就是预期的那份业务状态。参考：[主程序符号的导出与解析](https://man7.org/linux/man-pages/man3/dlopen.3.html)。

加载之后，还要管理共享库的生命周期。只要后续仍可能执行其中的代码，就不能随意释放加载引用。本例让共享库保留到进程退出，暂不处理卸载。实际回收补丁时，还需要考虑线程是否仍在执行其中的代码。

现在，新函数已经可以调用，运行时地址也已拿到。剩下的问题是：怎样保留 `run_once()` 原有的调用指令，让这次调用执行新实现？


## 替换的关键：让旧函数入口跳向新函数

上一节已经把新函数加载到进程中，但 `run_once()` 的调用路径没有改变，再次调用时，结果仍然是 `22`。

如果程序通过函数指针调用，修改指针就可以让后续调用转向新函数。不过，第二节中展示的是直接调用：

```asm
call calculate
```

这条指令不会读取我们在 `dlsym()` 之后定义的函数指针。修改那个指针变量，只会影响使用它的调用。


### jmp 跳转到新函数

对于这里的直接调用，可以保留调用点，在 `calculate` 的入口将执行流程转向新函数：

![jmp_progress](https://raw.githubusercontent.com/ChnjFan/img-bed/master/img/20260901111922555.png)

调用者仍然进入原来的地址，只是到达入口后，马上跳转到新函数。原函数体可以继续留在内存中，这条调用路径已经不再执行它。本文所说的函数“替换”，就是**让后续经过旧入口的调用转向新实现**。

这里使用 `jmp`，是因为调用者执行 `call calculate` 时已经保存了返回地址。只要在原函数建立栈帧之前跳走，并且新函数遵守相同的调用约定，新函数就能沿用原来的参数和栈状态。执行 `ret` 时，它也会沿着原来的返回地址回到调用者。

{{< notice note >}}
`jmp` 是 x86 汇编里的无条件跳转指令，直接修改 `EIP/RIP`（指令指针寄存器）的值，CPU 不再顺序执行下一条指令，跳到指定地址继续运行，**不影响标志位**。
{{< /notice >}}

`jmp` 不会额外压入返回地址。如果在这里改用 `call calculate_v2`，又没有配套的包装逻辑，新函数就会返回到这条 `call` 后面，也就是旧入口附近，而不是直接回到原调用者。入口处使用跳转，保留了原来“调用一次、返回一次”的关系。


### 如何将 jmp 写进内存

x86-64 提供了多种跳转形式。常见的一种是五字节相对跳转：

```
E9 + 4 字节有符号位移
```

目标地址以跳转指令结束后的位置为基准计算，位移范围约为正负 2 GiB。主程序和动态加载的共享库未必相距这么近，因此拿到两个地址后，不能直接把差值截断为四个字节。参考：[Intel 指令手册中的 JMP](https://cdrdv2-public.intel.com/789581/325383-sdm-vol-2abcd.pdf)。

本例采用另一种布局：

```
FF 25 00 00 00 00          6 字节跳转指令
xx xx xx xx xx xx xx xx    8 字节新函数地址
```

前六个字节对应的 AT&T 汇编指令是：

```asm
jmp *0(%rip)
```

处理器执行这条指令时，会从紧接着指令的内存位置读取一个八字节地址，再跳转到该地址。这段布局由**六字节指令和八字节地址数据组成**，共占十四字节，并不是一条十四字节长的指令。执行流程已经跳走，后面的地址数据不会被顺序当作指令执行。

这种跳转不占用通用寄存器，也不要求新函数位于旧入口附近。不过，选好了跳转形式，还不能直接覆盖任意函数入口。第二节的反汇编中，入口后面紧接着就是原函数的指令：

```asm
endbr64
push   %rbp
mov    %rsp,%rbp
mov    %edi,-0x4(%rbp)
...
```

这段代码没有预留补丁空间。直接覆盖入口处的字节，可能破坏原有指令，影响仍在执行旧代码的线程，也会给恢复原逻辑或构造跳板带来麻烦。x86 指令长度不固定，任意截取的几个字节可能只是某条指令的一部分。

示例程序因此需要重新编译，为目标函数预留入口空间：

```cpp
extern "C"
__attribute__((noinline, patchable_function_entry(16, 0)))
int calculate(int x) {
    return x + 1;
}
```

`patchable_function_entry` 用来在函数入口附近插入 NOP。具体布局受目标平台和编译选项影响，编译后仍需检查生成的指令，不能仅凭这个属性就认定入口布局符合要求。参考：[GCC 函数入口预留机制](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html#index-fpatchable-function-entry)。

本例生成以下布局：

```asm
0000000000001229 <calculate>:
    1229:       f3 0f 1e fa             endbr64
    122d:       90                      nop
    ...   一共 16 个 nop 单字节
    123d:       55                      push   %rbp
    123e:       48 89 e5                mov    %rsp,%rbp
    1241:       89 7d fc                mov    %edi,-0x4(%rbp)
    1244:       8b 45 fc                mov    -0x4(%rbp),%eax
    1247:       83 c0 01                add    $0x1,%eax
    124a:       5d                      pop    %rbp
    124b:       c3                      ret
```

安装补丁时，我们保留 endbr64，将跳转写入它后面的 NOP 区域。新函数入口也要求带有 endbr64，因为这里采用间接跳转，需要满足 CET 间接分支跟踪对目标入口的要求。不过，入口处存在这条指令，并不能说明运行时已经启用了相关检查。参考：[Intel 间接分支跟踪说明](https://edc.intel.com/content/www/us/en/design/products/platforms/details/raptor-lake-s/13th-generation-core-processors-datasheet-volume-1-of-2/004/indirect-branch-tracking/)。

补丁安装后的布局变为：

```
calculate 入口：
    endbr64                 保留

预留区域：
    jmp *0(%rip)            6 字节
    新函数的运行时地址         8 字节
    nop                     剩余 2 字节
    nop

原函数体：
    保留，但这条调用路径不再进入
```

这个演示需要**提前重新编译宿主，预留出上述空间**，不能直接用于第二节那份没有 NOP 区域的二进制。它只演示入口跳转机制，并不是通用的二进制补丁器。

下面是[完整示例](https://github.com/ChnjFan/CodeGuide/blob/main/C%2B%2B/source/patch/host.cpp)中构造补丁字节的代码。`replacement` 是一个十六字节数组，`new_function` 是上一节通过 `dlsym()` 取得的新函数地址：

```cpp
replacement.fill(0x90);

const unsigned char opcode[] = {
    0xff, 0x25, 0, 0, 0, 0
};

const auto target = reinterpret_cast<std::uintptr_t>(new_function);
static_assert(sizeof(target) == 8);

std::memcpy(replacement.data(), opcode, sizeof(opcode));
std::memcpy(replacement.data() + sizeof(opcode), &target, sizeof(target));
```

x86-64 使用小端字节序，这里将八字节地址按本机表示复制到指令后面。数组剩下的两个字节继续保持为 NOP。

写入补丁前，还需要修改代码页的权限。普通代码页通常可读、可执行，但不可写，直接用 `memcpy()` 覆盖可能触发访问错误。Linux 的 `mprotect()` 可以修改页权限，但起始地址必须按页对齐，权限变更也以页为单位。同一页上的其他函数可能一起受到影响。参考：[Linux mprotect 手册](https://man7.org/linux/man-pages/man2/mprotect.2.html)。

完整示例按以下顺序安装补丁：

1. 核对新旧函数入口的 `endbr64`，以及旧入口后面的十六个 NOP。
2. 确认补丁区域位于同一个原本为私有 `RX` 的映射页内，并备份原字节。
3. 临时将该页设为可读、可写、可执行，写入补丁字节。
4. 恢复原来的 `RX` 权限，处理指令流同步，核对写入结果。
5. 再次调用 `run_once()`。

临时允许代码页同时可写、可执行，是示例的一处简化。系统安全策略可能拒绝这种权限变更，此时应停止安装，不能关闭防护或强行绕过。如果写入后无法恢复 `RX` 权限，示例也会直接终止进程，不再继续执行。

写完内存并不意味着指令流已经同步。示例还需要遵守处理器对自修改代码的执行要求，因此在写入后使用 `CPUID`，对当前处理器上的指令流进行序列化。它不代表其他线程也已完成同步。`__builtin___clear_cache()` 在某些目标上可能不生成任何操作，也不能用于协调线程。参考：[Intel 自修改代码说明](https://cdrdv2-public.intel.com/868137/325462-089-sdm-vol-1-2abcd-3abcd-4.pdf)、[GCC 指令缓存处理接口](https://gcc.gnu.org/onlinedocs/gcc-12.2.0/gcc/Other-Builtins.html)。

本节实验因此限定在自行启动的单线程程序中。安装补丁时，旧函数已经返回，也没有信号处理函数会重新进入它。写入十六字节的 `memcpy()` 本身不保证原子切换。

完整示例继续使用上一节的 `calculate_v2`，构建命令如下：

```bash
g++ -std=c++17 -O0 -fno-lto -fcf-protection=branch \
  -Wall -Wextra -Werror=attributes \
  -fPIC -shared patch.cpp -o patch.so

g++ -std=c++17 -O0 -fno-lto -fcf-protection=branch \
  -Wall -Wextra -Werror=attributes \
  host.cpp -ldl -o host
```

运行前，通过反汇编检查原函数的预留区域、新函数入口，以及调用者中保留下来的调用指令：

```bash
objdump -d --disassemble=calculate host
objdump -d --disassemble=run_once host
objdump -d --disassemble=calculate_v2 patch.so
```

入口布局不符合前述条件，就停止安装。完整代码也会检查实际字节，发现不匹配便退出。在满足这些前提的环境中运行 `./host`：

```
before: 22
loaded: 22
patched: 24
restored: 22
```

四个阶段中，原来的 `run_once()` 分别沿着以下路径执行：

| 阶段 | 执行路径与结果 |
|---|---|
| 加载之前 | 执行旧函数，得到 `(10 + 1) × 2` |
| 只加载共享库 | 调用路径没有改变，仍然执行旧函数 |
| 安装入口跳转 | 经过旧入口跳到新函数，得到 `(10 + 2) × 2` |
| 恢复入口字节 | 再次进入旧函数体 |

恢复时，程序将安装前保存的原始 NOP 字节写回入口。本例只做纯计算，因此恢复调用路径就能恢复原来的计算行为。如果新函数已经修改了业务数据，恢复入口并不会撤销这些修改。

备份原字节与构造 trampoline（跳板）也需要分清。备份字节用于日后恢复入口；如果新实现还要调用旧实现，仅有备份并不够。直接调用 `calculate()` 会再次经过补丁入口，可能形成递归。

某些实现会将入口处被覆盖的完整指令迁移到另一块可执行区域，执行这些指令后，再跳回原函数中未被覆盖的位置。这样就保留了一条调用旧实现的路径，微软 Detours 采用的就是这种思路。参考：[Detours 的入口修改与 trampoline](https://github.com/microsoft/Detours/wiki)。

迁移指令也未必能原样复制。遇到 RIP 相对寻址或相对分支，指令位置变了，原位移可能就不再指向同一个目标。本节用预留 NOP 避开了这部分复杂性，也不需要调用旧实现，因此没有构造通用 trampoline。

入口跳转让同一进程中的同一处 `run_once()` 调用有了执行新函数的路径。不过，示例还没有处理多线程切换：写入跳转时，如果另一个线程恰好经过入口，或仍在执行旧函数，会发生什么？下一节讨论这些执行状态与补丁切换时机。


## 函数正在执行时，补丁该怎样切换

上一节选择了一个容易控制的时机：`calculate()` 已经返回，程序只有一个线程，下一次调用还没发生。我们可以利用两次调用之间的空隙修改入口，再观察结果。

线上程序通常没有这样的空隙。管理线程准备安装补丁时，业务线程可能正要调用目标函数，也可能已经进入函数体，甚至还在等待函数内部发起的一次 I/O。此时，安装补丁需要同时处理三个问题：

| 问题 | 需要保证什么 |
|---|---|
| 入口指令的修改 | 没有线程执行到不完整或错误的指令序列 |
| 旧调用的处理 | 已经开始的调用仍有合法的继续执行和返回路径 |
| 新旧逻辑的衔接 | 切换前后的代码能够正确处理业务状态 |

这三个问题相互关联，但解决其中一个，并不代表其余两个也已解决。

上一节用 `memcpy()` 将跳转指令和目标地址写入十六字节的预留区域。这个复制操作不保证其他线程一次性看到完整的新内容。如果业务线程在写入期间进入这片区域，就可能遇到新旧字节混杂的状态。例如，跳转指令已经写好，后面的目标地址却只写了一部分，线程可能因此跳到错误地址或异常退出。

将代码页设为可写，只解决了写权限问题。写入后核对字节，也只能确认检查那一刻的内容，不能证明其他线程没有执行过写入过程中的中间状态。跨处理器修改代码还需要满足相应的同步要求，不能只按普通数据读写来处理。参考：[Intel 跨处理器代码修改要求](https://cdrdv2-public.intel.com/671294/252046-sdm-change-document.pdf)。

一个比较容易想到的方案是**先暂停业务线程，写完再恢复**，看起来可以避免并发执行。但暂停之后，还需要检查线程停在什么位置。假设一个线程执行到 NOP 预留区域的中间时被暂停。管理线程随后将这片区域改成跳转指令和地址数据，再恢复业务线程。线程通常会从保存的指令位置继续执行，不会自动回到函数入口。

```
修改前：
    endbr64
    nop
    ...
    nop  ← 线程暂停的位置
    ...

修改后：
    endbr64
    跳转指令
    新函数地址数据
         ↑ 原来保存的执行位置可能落到这里
```

即使恢复线程时所有字节都已写好，它接下来执行的位置也可能不合法。因此，修改入口时还需要检查被暂停线程的执行位置，确认它们停在安全区域；如果要调整线程上下文，则必须有正确的位置映射规则。Detours 的线程更新接口就涉及改写区域内指令指针的处理。不过，这是 Windows 实现中的例子，不能直接作为 Linux 的操作步骤。参考：[Detours 线程更新说明](https://github.com/microsoft/Detours/wiki/DetourUpdateThread)。

**对于已经进入旧函数体的调用，修改入口不会让它自动转入新函数**。如果线程已经越过入口，后续需要执行的旧代码也仍然保留，就可以考虑让这次调用继续执行旧版本，后续调用再进入新版本。

下面是一条假设的时间线，前提是入口修改已经安全完成，而且新旧版本允许在过渡期间共存：

| 时刻 | 线程 A | 补丁管理线程 | 线程 B |
|---|---|---|---|
| T1 | 进入旧函数体 | 准备补丁 | 尚未调用 |
| T2 | 仍在执行旧函数 | 安全完成入口切换 | 尚未调用 |
| T3 | 继续执行旧逻辑 | 切换完成 | 从入口进入新函数 |
| T4 | 旧调用返回 | — | 执行新逻辑并返回 |

这段时间里，进程同时执行两个版本的代码。对于上一节中只根据参数计算结果的函数，这种安排比较容易理解。但业务函数是否允许这样切换，需要单独判断，不能把它当成所有热补丁的默认规则。

另一种思路是**等旧调用全部结束，再允许新调用进入**。这里的顺序不能颠倒：先阻止新调用进入，再等待已有调用结束。如果管理线程只是观察到“当前没有线程执行目标函数”，随后就开始写入，新的调用仍可能在检查与写入之间进入。一次状态检查并不能保证接下来的切换过程安全。

对于能够配合修改的程序，可以在函数调用之前设置准入机制：

1. 暂时阻止新的相关操作进入。
2. 等待已经获准进入的操作完成。
3. 在约定的安全状态下修改入口，完成必要的指令流同步。
4. 确认切换成功，再允许后续操作进入。

“相关操作”可以是一次函数调用，也可以是一个完整请求，取决于业务需要在哪个范围内保持一致。

仅给补丁管理线程加锁，保护不了业务线程的执行路径。业务线程也必须遵守同一套协议，在进入可能被改写的指令之前取得许可。如果锁写在目标函数体内部，线程到达锁之前就已经经过了入口，这个锁无法保护入口指令。

这种设计通常称为**在安全点切换**。安全点需要满足一组可以验证的条件：**相关旧操作已经结束，新操作暂时无法进入，恢复执行后也不会落入失效的指令位置**。仅指定某一行代码，还不足以保证这些条件成立。

因此，不重启进程也可能需要短暂停顿。程序可以保留进程和内存状态，同时暂停某类请求的进入。暂停范围有多大、需要等待多久，取决于框架与业务如何配合。

**指令流同步还要单独处理**。上一节中的 `CPUID` 只作用于执行它的处理器，管理线程执行过一次，并不代表所有业务线程都完成了所需同步。Linux 提供了带有 `SYNC_CORE` 语义的 `membarrier` 命令，可用于相关同步，但使用前需要查询支持情况，并按要求注册。它不会阻止业务线程进入目标函数，也不会让多字节写入变成原子操作。参考：[Linux membarrier 的同步保证](https://man7.org/linux/man-pages/man2/membarrier.2.html)。

这些措施主要保证程序能沿着合法的指令路径执行，业务状态还可能带来其他要求。假设旧函数按秒写入某个超时时长字段，新函数却按毫秒解释它。即使字段访问有锁、对象布局也没变，新旧逻辑混用时仍可能出错。锁能安排访问顺序，却不会自动转换数据单位。

即便新旧函数各自都能正确处理当前状态，一次请求也可能跨过切换时刻：

```
请求开始
    第一次调用：执行旧函数
    安装补丁
    第二次调用：执行新函数
请求结束
```

如果业务要求同一个请求始终使用同一套规则，仅在单次函数调用之间切换就不够。可能需要等待整个请求结束，或者设置版本化的调用入口，让请求在开始时确定使用哪个实现。

设计切换协议前，需要明确补丁承诺哪种行为：切换后进入函数的调用使用新版本，还是切换后开始的请求整体使用新版本？两者需要协调的范围不同。

旧代码何时可以释放，也需要单独判断。本例的原函数位于主程序中，始终保留在内存里。实际框架如果要卸载旧补丁库或释放 `trampoline`，就必须确认后续没有执行路径会再使用这段代码。

仅检查线程当前的指令位置还不够。例如：

```
旧函数
    -> 调用某个辅助函数
        -> 线程当前停在辅助函数里
    <- 辅助函数结束后，还要返回旧函数
```

线程当前虽然没有执行旧函数，栈上却保留着返回旧代码的路径。已经保存的函数指针、尚未执行的回调，也可能稍后再次使用旧代码。

`dlclose()` 管理共享对象的加载引用，不会替应用程序确认这些执行路径是否已经消失。而且，即使它成功返回，共享对象也不一定已经从进程地址空间中移除。参考：[Linux dlclose 语义](https://man7.org/linux/man-pages/man3/dlopen.3.html)。

入口切换与旧代码回收因此往往分开进行：先让新调用转向新版本，再等待旧版本不再被执行或引用，最后才考虑释放。回滚也需要遵守这些条件，恢复原字节时同样不能省略线程协调。

除了让调用跳到新函数，热补丁还需要确定安全的切换时机，并判断切换后哪些状态仍然有效。C++ 的参数、返回值、对象布局、内联和虚函数又会带来哪些限制，是接下来要讨论的问题。


## 为什么 C++ 的某些修改不能直接打补丁

前面的示例选择了一个简单函数：参数和返回值都是 int，不依赖已有对象，调用也明确经过可修改的入口。实际的 C++ 函数可能通过 this 访问对象，使用静态变量，调用模板实例，或者已经被编译器内联到多个调用者中。

判断一次修改能否做成热补丁，需要检查新实现是否兼容旧调用者、能否正确访问已有状态，以及待修复的执行路径是否经过被替换的入口。源码改了几行，并不能回答这些问题。

以参数为例，原来的函数声明是：

```cpp
int calculate(int x);
```

现在增加一个带默认值的参数：

```cpp
int calculate(int x, int bias = 2);
```

源码中的 `calculate(10)` 仍然可以编译，但正在运行的旧调用者没有重新编译，只会按原接口准备参数。在前面的 x86-64 示例中，它将 `10` 放入 `EDI`，并没有按新接口准备第二个参数 `ESI`。跳到新函数之后，默认值 2 不会自动出现在那里。

默认实参在调用表达式所在的调用点参与编译，由调用者按照 ABI 传递。被调用函数不会在运行时检查缺少了几个参数，再替调用者补齐。参考：[C++ 默认实参规则](https://eel.is/c++draft/dcl.fct.default)。

因此，源码层面兼容的修改，到了二进制层面未必兼容。如果新实现确实需要增加参数，可以考虑保留原来的外部入口，由兼容旧调用约定的函数补齐参数，再调用新的内部实现。前提是新增参数有合理的来源，补齐后的行为也符合业务要求。

返回值的变化同样需要检查。将整数返回值改为对象，或改变对象的传递方式，都可能改变返回值的位置，甚至引入隐含的返回对象地址。新旧函数都能编译，不代表它们的入口可以直接互换。参考：[C++ ABI 的函数调用接口](https://itanium-cxx-abi.github.io/cxx-abi/abi.html#calls)。

`extern "C"` 也不能解决这些兼容性问题。它可以简化符号命名，却不会检查参数类型、返回值类型和对象布局。

成员函数还涉及已有对象。它可以通过隐含的 `this` 参数访问对象，但新函数即使收到了正确的地址，也必须按旧对象的实际布局解释这段内存。

下面用两个版本说明布局变化带来的问题。它们是独立的类型定义，不应在同一个程序中作为同一种类型同时使用。

```cpp
// 旧版本
struct Counter {
    int limit;
    int used;
};
// 新版本在中间加了字段
struct Counter {
    int limit;
    int flags;
    int used;
};
```

在本例的 Linux x86-64 环境中，类没有使用特殊的打包设置，int 占四字节。新旧对象的布局如下：

| 相对对象起始地址的偏移 | 旧对象 | 新代码预期的对象 |
|---|---|---|
| `+0` | `limit` | `limit` |
| `+4` | `used` | `flags` |
| `+8` | 已超出旧对象范围 | `used` |
| 对象大小 | 8 字节 | 12 字节 |

如果进程中已经存在按旧定义创建的对象，加载新函数不会将这些对象自动扩展到十二字节。新函数按照新布局读取 used 时，会访问对象起始地址加八的位置，已经越过旧对象的边界。`this` 保存的地址虽然没有变化，新代码对这段内存的解释却变了。

将新字段追加到类的末尾，也不能直接认定为安全。原有字段的偏移可能保持不变，但对象大小、数组步长、分配空间以及构造和析构逻辑仍可能发生变化。

修改成员函数体和修改类定义需要分别评估。前者如果不破坏对象布局和状态语义，可能适合函数级替换；后者通常还需要处理已有对象，例如迁移数据、使用额外存储，或者通过版本化方式访问对象。这些工作已经超出了修改函数入口所能完成的范围。

编译优化还会带来另一个问题：源码中存在某个函数，不代表运行时的每次调用都会经过它的独立入口。如果去掉示例中的 `noinline` 并启用优化，编译器可能把 `calculate(10)` 的逻辑直接放进 `run_once()`，甚至把最终结果折叠成常量。此时，即使修改了独立的 `calculate` 入口，已经嵌入调用者的旧逻辑也不会改变。

```
仍保留调用：
    run_once → calculate 入口 → 函数体
                    ↑
                 入口补丁有效

已被内联：
    run_once 内部直接执行原计算逻辑
                    ↑
          不再经过 calculate 入口
```

判断函数是否被内联，需要检查实际生成的机器代码，不能只在源码中搜索 `inline`。没有显式写 `inline` 的函数也可能被编译器内联。反过来，只给补丁中的新函数增加 `noinline`，也无法改变已经运行的宿主代码。

内联也不是唯一需要考虑的优化。编译器可能生成函数的特化副本，还可能利用函数体信息优化其他调用者。因此，源码中只修改了一个函数，并不代表最终只需替换一个入口。

GCC 的 `-flive-patching` 文档使用“受影响函数”描述这类关系：如果编译器在优化其他函数时用到了目标函数的实现，制作补丁时也需要考虑这些依赖。这个选项可以约束相关优化，但不会自动生成或安装热补丁。参考：[GCC 对热补丁与优化影响范围的说明](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html#index-flive-patching)。

模板函数同样要从编译产物出发分析。一个函数模板可能生成多个实例，例如 `calculate<int>` 和 `calculate<long>`，这些实例又可能被内联到不同的调用者中。修改模板源码后，需要确认进程中实际生成了哪些实例，执行路径又经过哪些代码。

因此，模板函数并非一概不能打补丁，重新编译模板也不会自动更新进程中的所有旧实例。补丁最终替换的仍然是已经生成的机器代码。

虚函数多了一层调用路径。在常见实现中，虚调用通过对象关联的虚表找到目标入口；遇到复杂继承时，中间还可能经过调整 `this` 的 `thunk`。虚表、`thunk` 和最终函数体之间是什么关系，需要结合 ABI 和实际编译产物判断。参考：[C++ ABI 的虚函数调用约定](https://itanium-cxx-abi.github.io/cxx-abi/abi.html#vcall)。

对于虚函数，需要区分下面两种修改：

- **修改虚表项**：改变经过这个表项的调用目标。
- **修改函数入口**：改变经过这个代码入口的执行路径。

两者覆盖的调用范围并不相同。

编译器还可能把虚调用优化成直接调用，这称为去虚拟化。去虚拟化后的调用不再读取虚表项，但仍可能经过目标函数入口；如果编译器进一步将函数内联，调用才会连独立入口也绕过。参考：[GCC 去虚拟化说明](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html#index-fdevirtualize)。

虚函数并不会天然让热补丁更容易。只修改函数实现时，需要核对目标入口和 `this` 的传递约定。增加或删除虚函数、改变继承关系时，还要检查虚表与对象布局是否兼容。

函数内部的静态变量也容易被忽略。假设某个函数首次执行时初始化了局部静态对象，之后修改初始化表达式并替换函数入口，原对象不会因此自动重新初始化。按照 C++ 的局部静态变量初始化规则，一次成功的初始化不会在后续经过该声明时重复执行。参考：[C++ 局部静态变量初始化规则](https://eel.is/c++draft/stmt.dcl)。

热补丁还需要确认新代码访问的是哪份存储。它可能继续使用旧对象，也可能因为符号和装载方式不同而产生另一份对象。前一种情况要判断旧状态是否仍然可用，后一种情况则要防止状态被意外拆成两份。全局变量和线程局部变量也需要检查各自的符号绑定与生命周期。

即使新旧函数的声明看起来相同，仍然需要核对构建兼容性。补丁跨边界传递 `std::string` 等标准库类型时，相关 ABI 配置必须一致。`libstdc++` 的 `_GLIBCXX_USE_CXX11_ABI` 会影响部分类型的 ABI，而且它的选择独立于 `-std` 选项。宿主和补丁都使用 `-std=c++17`，不能据此认定二者兼容。参考：[libstdc++ 双 ABI 说明](https://gcc.gnu.org/onlinedocs/libstdc++/manual/using_dual_abi.html)。

如果边界上还涉及异常传播、对象构造与析构，以及内存的分配和释放，也要确认双方使用的运行库与调用约定能够配合。补丁的构建配置应以目标程序的实际产物为准，不能临时选择一组看起来相近的编译参数。

这些限制可以整理为一张制作补丁前的检查表：

| 修改类型 | 重点检查 |
|---|---|
| 修改普通函数体 | 调用约定是否保持兼容，相关调用是否经过目标入口 |
| 增加参数或改变返回类型 | 旧调用者能否继续调用，是否需要兼容入口 |
| 修改成员函数 | `this` 的含义、字段偏移和已有对象状态是否兼容 |
| 增删字段或改变继承关系 | 对象大小、布局、构造析构与迁移方案 |
| 修改内联函数或模板 | 已生成的实例、内联位置和受影响调用者 |
| 修改虚函数 | 虚表、thunk、直接调用与内联路径的覆盖范围 |
| 修改静态或全局状态 | 新代码绑定哪份存储，初始化和生命周期如何衔接 |
| 更换编译器或构建配置 | ABI、标准库、运行库及代码生成差异 |

这份检查表不能代替具体框架判断某次修改是否可以打补丁。它用于确认源码变化会影响运行中程序的哪些调用约定、代码路径和已有状态。

回到最初的操作流程，制作工具收到的是函数级修改，但要生成可靠的补丁，还必须将这些修改与目标程序的实际构建产物对应起来。接下来再把加载、定位、切换、验证和回滚串回那条管理命令，看看一次补丁“生效”到底需要哪些保障。


## 回到管理命令：一次补丁生效还需要哪些保障

回到最初看到的操作流程：

```
提交修改后的函数代码
    → 内部工具制作补丁包
    → 通过管理命令加载
    → 补丁生效
```

经过前面的分析可以看出，“制作补丁包”和“加载生效”各自包含一系列具体工作。

制作阶段需要将源码编译成与目标程序兼容的机器代码，并记录如何定位旧函数、加载新函数，以及改变原有调用路径。加载阶段则需要校验目标程序，建立安全的切换窗口，写入跳转并验证结果，同时保存回退所需的信息。

我们不知道内部工具采用什么格式，但从实现机制看，一个函数级补丁至少需要描述以下内容：

```yaml
patch:
  id: "补丁的唯一标识"

target:
  architecture: "x86-64"
  module: "目标可执行文件或共享库"
  build_id: "目标构建标识"

replacement:
  old_function: "原函数标识或模块内偏移（可以与模块装载基址相加的虚拟地址偏移）"
  expected_entry: "应用补丁前应看到的入口字节"
  new_object: "承载新函数的共享对象"
  new_function: "新函数符号"

strategy:
  type: "entry_jump"
  required_space: "需要覆盖或预留的长度"
  synchronization: "切换时采用的协调方式"

compatibility:
  compiler_and_abi: "需要满足的构建兼容条件"
  dependencies: "新函数依赖的符号和版本"
```

这份清单只用于说明补丁包需要描述哪些信息，不代表内部工具采用 YAML，也不代表所有实现都通过共享库加载新代码、修改函数入口。

目标构建标识用于确认补丁是否对应当前程序。同一个函数名可能出现在程序的多个版本中，但函数地址、入口指令、对象布局和调用者都可能不同。

GNU 链接器可以在 `ELF` 中生成 `.note.gnu.build-id`，用于标识链接产物。`Build ID` 可以帮助补丁系统判断目标构建，却不是当前文件内容的完整校验和。如果链接产物后来被其他工具修改，原有 `Build ID` 不会自动更新。参考：[GNU ld 的 Build ID 说明](https://sourceware.org/binutils/docs/ld/Options.html#index-build-id)。

运行时通常需要组合检查多项信息：

- 进程和目标模块是否符合预期；
- CPU 架构与 ABI 是否匹配；
- Build ID 是否对应；
- 目标函数在模块中的位置是否一致；
- 函数入口是否仍然保留制作补丁时记录的原字节；
- 是否已有其他补丁修改了同一片区域。

入口字节需要单独核对。即使版本标识匹配，如果另一个补丁已经改写了函数入口，继续覆盖也可能破坏原补丁的跳转或回滚信息。

目标校验完成后，还要计算函数在当前进程中的地址。第二节反汇编里的 `0x1129` 是 `ELF` 映像中的位置，不能直接当作每次运行时的绝对地址。启用地址空间布局随机化后，模块的装载基址可能发生变化。

一种定位方式是先找到目标模块的运行时基址，再加上制作补丁时记录的模块内偏移：

```
运行时函数地址 = 模块运行时基址 + 函数在模块内的偏移
```

Linux 的 `/proc/<pid>/maps` 可以显示进程的内存映射、页面权限和对应文件。`dladdr()` 可以根据一个运行时地址查询它所属的共享对象、装载基址以及附近的符号。这些接口能提供定位信息，却不会自动处理符号缺失、同名函数或编译器生成的优化副本。参考：[进程内存映射](https://man7.org/linux/man-pages/man5/proc_pid_maps.5.html)、[dladdr 说明](https://man7.org/linux/man-pages/man3/dladdr.3.html)。

目标函数没有进入动态符号表时，也可以在离线制作阶段通过 ELF 符号、调试信息或构建产物确定模块内偏移。无论使用哪种定位方式，运行时都应再次核对目标位置的字节，不能只凭函数名认定地址正确。

确定目标后，可以把应用补丁分成准备和提交两个阶段。

**准备阶段**尽量完成不需要暂停业务线程的工作：

- 校验补丁包完整性和目标构建信息；
- 检查补丁依赖、ABI 与入口修改策略；
- 加载承载新函数的共享对象；
- 解析新函数及其依赖，取得运行时地址；
- 定位原函数并核对当前入口字节；
- 准备跳转内容、原字节备份和回滚记录。

使用 `RTLD_NOW` 调用 `dlopen()`，可以要求共享库中需要解析的未定义符号在函数返回前完成解析。解析失败时，加载也会失败。不过，这只能说明动态加载器满足了相关链接要求，不能证明新函数的类型、业务逻辑或状态访问是正确的。参考：[dlopen 的解析选项](https://man7.org/linux/man-pages/man3/dlopen.3.html)。

共享库的初始化函数会在 `dlopen()` 返回前执行。也就是说，即使准备阶段还没有修改函数入口，加载本身仍可能产生业务副作用。补丁设计需要限制初始化行为，并将可能发生的状态变化纳入失败处理。

准备成功后，**提交阶段**才真正改变执行路径：

- 阻止新的相关操作进入切换区域。
- 等待或处理仍在执行的旧调用。
- 再次确认入口字节与准备阶段一致。
- 按目标平台要求修改代码页权限。
- 写入跳转，完成跨线程和跨处理器的指令流同步。
- 恢复代码页权限。
- 核对写入后的字节与目标地址。
- 允许后续调用继续进入。

将准备和提交分开，可以减少业务线程真正需要协调的时间。但两者之间仍可能发生状态变化，因此提交前必须重新校验准备阶段得到的信息。

整个过程可以表示为一个状态机：

![path-progress](https://raw.githubusercontent.com/ChnjFan/img-bed/master/img/20260901105504627.png)

这些状态还可以帮助管理命令安全重试。假设第一次命令已经完成入口切换，却在返回结果前断开连接。再次执行命令时，补丁系统不能直接重写入口，而要结合补丁 ID、当前入口字节和进程内记录，判断补丁尚未开始、已经准备完成、已经激活，还是进入了需要人工处理的异常状态。

多个补丁可能修改同一个函数，也可能彼此依赖。补丁管理器需要将冲突操作串行化，记录当前入口由哪个补丁管理，并明确回滚时应恢复到程序的原始版本，还是恢复到上一个补丁版本。只保存程序最初的入口字节，无法正确处理补丁叠加后的各种回滚顺序。

入口写入成功，只能说明跳转已经安装，不能说明补丁已经通过验证。验证可以分为几个层次：

| 验证层次 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 补丁包校验 | 文件、版本和元数据符合预期 | 新代码能够正确执行 |
| 加载校验 | 共享对象和依赖能够解析 | 原调用已经转向新函数 |
| 结构校验 | 入口字节、跳转目标和页权限正确 | 业务请求一定经过该入口 |
| 执行校验 | 选定的探针或测试调用执行了新代码 | 所有输入和状态都能正确处理 |
| 业务观测 | 故障表现及相关指标是否改善 | 改善一定由补丁单独造成 |

示例中，结果从 22 变为 24，可以证明 `run_once()` 已经执行了新函数。真实的业务函数却未必适合由管理线程直接调用，特别是函数依赖请求上下文或会修改业务状态时。

一种可选做法是让**新实现暴露可识别的版本信息，或者维护受控计数**，用来确认真实调用已经进入新代码。探针本身仍要评估性能开销、线程安全和隐私影响。确认执行路径后，还要继续观察原故障对应的现象，不能只看到管理命令返回“成功”就结束验证。

验证失败时，需要区分代码回滚和业务回滚。代码回滚通常包括重新建立安全切换窗口、恢复入口字节、完成指令流同步，并确认后续调用重新进入旧版本。

这些操作只能恢复代码路径。新函数已经写入的数据、发出的外部请求或改变的缓存状态，不会随入口恢复而自动撤销。补丁是否容易回滚，很大程度上取决于新函数的副作用。如果新旧逻辑写入的数据格式不同，还要在安装前确认旧代码能否读取切换期间产生的数据。

恢复入口后，新函数所在的共享库也不能立即卸载。仍在执行新函数的线程、栈上的返回路径、已经保存的函数指针和尚未执行的回调，都可能继续引用其中的代码。入口回滚和新代码回收，需要采用与安装时同等严格的线程与生命周期判断。

管理命令最终可以区分以下结果，避免用一个含义模糊的“成功”覆盖所有阶段：

| 结果 | 含义 |
|---|---|
| 已准备 | 补丁与目标匹配，新代码已经加载，原入口尚未改变 |
| 已激活 | 入口切换和结构检查完成，后续调用可以进入新代码 |
| 已验证 | 至少一项预先定义的执行验证或业务验证通过 |
| 已回滚 | 入口已经恢复，同时还要说明业务副作用和代码回收状态 |
| 失败且状态不确定 | 无法证明入口处于完整的新版本或旧版本，进程不应继续正常承载业务 |

现在可以重新回答文章开头的问题。

提交修改后的函数代码后，制作工具需要使用与目标程序兼容的环境生成机器代码，再将新代码、目标构建标识、定位信息、入口前置条件和回滚材料组织成补丁包。

管理命令开始加载时，新代码先进入目标进程，动态加载器完成必要的符号解析。补丁框架随后定位原函数，建立安全切换窗口，在函数入口写入跳向新函数的指令，并完成执行线程所需的同步。

切换完成后，调用者仍然调用原来的地址，但函数入口已经将执行路径引向新实现。已经进入旧函数的调用、进程中现有的 C++ 对象和业务状态，还要按照补丁定义的兼容性与一致性方案继续处理。

这条路径解释了函数级 C++ 热补丁如何从“补丁包已经加载”走到“运行中的函数已经被替换”。入口跳转是其中最容易观察的一步。目标校验、线程协调、ABI 兼容、状态处理、验证和回滚，才共同决定补丁能否安全用于线上程序。
